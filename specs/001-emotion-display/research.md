# Phase 0 研究

## 決策：以 Python 3.11＋Pillow 進行繪製
- **理由**：Raspberry Pi OS 原生可用，套件齊全，提供簡單 API 以繪製白底黑線條表情並輸出 PNG，無需重度 GPU 依賴。
- **替代方案**：C++／SDL（建置鏈較重）、Node／canvas（執行時負擔較大）、以 C 直接寫 framebuffer（迭代效率低）。

## 決策：使用 RGB565 透過 mmap 寫入 `/dev/fb0`
- **理由**：直接存取 framebuffer 可降低依賴與延遲；RGB565 符合 Waveshare 契約，寫入行為可預期。
- **替代方案**：`fbi`／`fbv` 子行程（增加安裝與執行依賴、控制性低）、Python 綁定的 DRM/KMS（對靜態表情過度）、以自訂 C 驅動經 SPI 重繪（複雜度過高）。

## 決策：單一 CLI 入口並以旗標選擇目標
- **理由**：符合以指令呼叫的使用者故事，在 Pi 上部署簡單，且可決定輸出至 framebuffer 或 dry-run。
- **替代方案**：HTTP 服務（需常駐程序與管理）、長駐 daemon＋socket（營運負擔高）、僅提供程式庫 API（對操作人員不夠直觀）。

## 決策：採用 golden image 像素比對驗證
- **理由**：可重複驗證 framebuffer 與 dry-run 輸出，能順利整合 pytest；1% 偏差門檻符合規格。
- **替代方案**：人工目視（不可重複）、僅用 checksum（對小幅渲染變化過於脆弱）、感知雜湊（難以約束在 1% 像素偏差）。

## 決策：當 framebuffer 契約缺失時改用 dry-run
- **理由**：安全失敗可避免部分寫入，並以產生 PNG 回饋操作人員。
- **替代方案**：僅硬性失敗（無預覽）、盡力寫入（可能破壞顯示）、未確認就自動寫入（安全風險）。
