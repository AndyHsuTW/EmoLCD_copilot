# EmoLCD_copilot 憲章

## 核心原則

### 實機與 framebuffer 單一目標
所有輸出鎖定 Raspberry Pi 5 搭配 Waveshare 3.5" LCD (B) v2，解析度 480×320，色彩格式 RGB565，`/dev/fb0` 為唯一寫入介面。若需更動硬體、驅動或輸出目標，必須先提出變更紀錄、更新 README 與規格文件，並附上回滾方案。

### 繪圖管線與工具約束
優先使用 Python 3.11 搭配 Pillow 繪製畫面，以 mmap 或等效零拷貝方式寫入 RGB565，不得堆疊額外 GUI/視窗框架。轉換流程需列出：色彩空間、位元序、對齊方式與緩衝區尺寸，並以自動化檢查或離線比對驗證輸出一致性。

### 測試驗證與回歸防線
每項改動需提供最少一個自動或半自動檢查：色彩轉換單元測試、輸出緩衝區長度檢查，以及實機煙囪測試（可用預製圖樣或像素摘要）。變更前先寫（或更新）測試，驗證失敗後再實作，避免以人工肉眼為唯一驗證手段。

### 文件語言與可追溯性
所有輸出的文件（constitution.md、spec.md、plan.md、tasks.md、implement.md）一律使用正體中文；僅類別、函式、檔名等專有名詞保留英文。每次決策需在對應文件留下依據（硬體設定、測試結果、版本差異），避免口頭知識。

### 版本治理與安全變更
功能、驅動或介面改動遵循語意化版本：破壞性變更升級主版號，新增能力升級次版號，細微修訂升級修訂號。涉及裝置或系統層操作（sudo、裝置節點）需記錄最小權限與回滾步驟；缺乏回滾方案的改動不得合併。

## 附加限制
技術棧固定為 Python 3.11 + Pillow，並以直接寫入 framebuffer 為優先路線；若引入 .NET、ImageSharp 或 SkiaSharp，必須證明相容於 RGB565 並未增加額外 GUI 層。不得透過遠端桌面或 X11 轉譯畫面；任何驅動安裝腳本需標示來源與版本，並在文件中留下實測命令與輸出。

## 開發流程
工作流遵循「計畫 → 規格 → 任務 → 實作」四段式；在編寫 plan.md 前，必須完成憲章檢核，覆蓋：硬體鎖定、繪圖管線、測試策略、文件語言、回滾方案。所有 spec.md 必須列出實機測試情境與驗收條件；tasks.md 按優先度對齊使用者情境，並標註檔案路徑。提交前須確認 README 與最新變更一致，並保留實機驗證證據（輸出摘要、截圖或檢查指令）。

## 治理
本憲章優先於其他流程文件；違反時需先修補再合併。修訂需在變更說明中列出受影響區塊、版本號與生效日期；若增刪原則或流程，依語意化版本決定升級級別。每次提交與審查都需對照憲章與憲章檢核條目，缺項者不得通過。治理紀錄（版本、日期、修改內容）須存放於此檔並同步至相關模板。
